# Assay — ADR-sæt 000–010

**Projekt:** Assay — headless stat-resolver og patch-differ for Dark and Darker
**Dato:** 18. august 2026
**Baseline-datasæt:** Patch 6.12 / Hotfix #123, build `0.17.150.9384`
**v1-scope:** Stat-resolver + patch-diff. TTK-solver og counter-matrix er deferred til v2.

> ℹ️ **ADR-000, ADR-001 og ADR-010 nedenfor er erstattet af revision 2.**
> Se `ADR-rev2-amendments.md`. ADR-002 til ADR-009 er gældende som skrevet her.

---

## ADR-000 — Sprog, crate-layout og renhedskontrakt

**Status:** Superseded af rev 2

### Kontekst
Assay skal beregne fuldstændige, korrekte statblokke for Dark and Darker-loadouts og diffe dem på tværs af patchversioner. Spillet patches ugentligt; værktøjet skal overleve det. Kernen er ren matematik uden I/O. En web-frontend er sandsynlig i v3, men er ikke v1.

Den dominerende fejlklasse i domænet er ikke crashes — det er *stille forkerte tal*. Fem forskellige statstørrelser (Armor Rating, PDR, PDR Mod, Armor Penetration, True Damage) er alle numerisk "et tal med procent" men opfører sig fundamentalt forskelligt. I et dynamisk eller svagt typet sprog er de alle samme type, og en forveksling producerer et plausibelt resultat.

### Beslutning
**Rust.** Fem crates plus fixtures:

```
assay/
├── assay-core/     Ren domænelogik. Ingen I/O, netværk eller filsystem.
├── assay-data/     Versionerede datasæt, schema, loader, validering.
├── assay-diff/     Strukturel diff mellem datasætversioner og resolverede loadouts.
├── assay-scrape/   Hjælpeværktøj. Producerer forslag, aldrig sandhed. (Se ADR-003)
├── assay-cli/      Binær. Eneste crate der må skrive til stdout.
└── fixtures/       Golden tests med håndberegnede forventede værdier.
```

**Afhængighedsretning er ensrettet og håndhævet:**
`cli → diff → data → core`, samt `scrape → data`. `core` afhænger af intet internt. `data` afhænger aldrig af `scrape`.

**Renhedskontrakt:** en test i CI fejler hvis `assay-core` indeholder referencer til `std::fs`, `std::net`, `std::process`, `reqwest`, `tokio` eller `assay-data`. Renheden er et testet krav, ikke en konvention. Samme mønster som `vinkelvaerk_core`'s forbud mod `package:flutter/`.

### Konsekvenser
- ✅ Newtype-mønstret gør enhedsforveksling til compile errors (ADR-002)
- ✅ serde løser versionerede datasæt og strukturel diff nærmest gratis
- ✅ wasm-target giver frontend-vej i v3 uden at røre kernen
- ✅ Kernen kan testes uden fixtures på disk
- ❌ Langsommere iteration end C#/Dart i starten
- ❌ Fem crates er overhead for et v1 på denne størrelse — accepteret, fordi grænserne er det der holder projektet rent når det vokser

### Alternativer overvejet
**C#** — hurtigst for udvikleren, men bidrager intet teknisk: ingen Unity-kobling, ingen typefordel, og ville sløre den mentale grænse mod IronCore.
**Dart/Flutter** — rigtigt valg hvis UI var v1. Det er det ikke; v1 er et bibliotek plus CLI, og Flutter er forkert værktøj til en CLI.
**Python** — hurtigst til scraping, men netop det svage typesystem er den dokumenterede fejlkilde her.

## ADR-001 — Numerisk repræsentation og determinisme

**Status:** Superseded af rev 2

### Kontekst
Patch-diff er kun brugbar hvis "ændret" betyder ændret. Flydende komma introducerer platform- og rækkefølgeafhængig støj, hvilket producerer fantomdiffs og gør golden tests skrøbelige.

Spillets tal kræver mere præcision end først antaget. Fighterens base Action Speed er `0%`, men Rogue'ens er **7,8125%** — fire decimaler, og tydeligvis en binær brøk (7 + 13/16). Milli-enheder (1e-3) ville trunkere det.

### Beslutning
Intern repræsentation er **fixed-point `i64` i mikro-enheder (1e-6)**.

```rust
/// Fixed-point med skala 1e-6. 7,8125% lagres som 7_812_500.
#[derive(Copy, Clone, PartialEq, Eq, PartialOrd, Ord)]
pub struct Fixed(i64);

pub const SCALE: i64 = 1_000_000;
```

- Alle domænetyper (ADR-002) wrapper `Fixed`, ikke `f64`
- Al aritmetik er eksakt for addition og subtraktion; multiplikation runder med **banker's rounding** og dokumenteret rundingspunkt
- Division tillades kun via eksplicitte, navngivne funktioner der angiver rundingsregel
- `f64` må forekomme i præsentationslaget (`assay-cli`), aldrig i `assay-core`

**Determinismekrav:** samme input og samme datasætversion skal producere byte-identisk output på tværs af platforme og kørsler. Håndhævet som test (ADR-010).

### Konsekvenser
- ✅ Diffs er eksakte; ingen fantomændringer
- ✅ Golden tests er stabile på tværs af maskiner
- ✅ i64 ved 1e-6 har rigelig headroom for alle spillets størrelser
- ❌ Multiplikationskæder kræver eksplicit rundingsdisciplin
- ❌ Kurveopslag (attribut → derived) skal interpoleres i fixed-point — se ADR-004

## ADR-002 — Typesikkerhed for statstørrelser

**Status:** Accepted

### Kontekst
Se ADR-000. Fem størrelser, samme numeriske form, uforenelig semantik.

### Beslutning
Hver statstørrelse er en distinkt newtype over `Fixed`. **Ingen `From`, ingen `Into`, ingen `Deref` mellem dem.**

```rust
pub struct ArmorRating(Fixed);       // rå værdi, input til kurve
pub struct PdrPercent(Fixed);        // resultat af kurven, cappet
pub struct PdrMod(Fixed);            // multiplikativt lag ovenpå PdrPercent
pub struct ArmorPen(Fixed);          // reducerer forsvarerens ArmorRating
pub struct TrueDamage(Fixed);        // omgår hele kæden
pub struct PowerBonus(Fixed);
pub struct MoveSpeedAdd(Fixed);      // flad
pub struct MoveSpeedBonus(Fixed);    // procentuel
pub struct Attribute(i32);           // heltal, ikke Fixed
```

Operatorer implementeres **kun hvor de er semantisk gyldige**:
- `PdrPercent + PdrPercent` — gyldig (bonusser summeres)
- `PdrPercent + PdrMod` — **eksisterer ikke**; compile error
- `MoveSpeedAdd + MoveSpeedBonus` — **eksisterer ikke**

Konverteringer sker udelukkende gennem navngivne, dokumenterede funktioner der repræsenterer en faktisk spilmekanik:

```rust
pub fn pdr_from_armor(ar: ArmorRating, curve: &Curve, cap: PdrPercent) -> PdrPercent;
pub fn apply_pdr_mod(base: PdrPercent, m: PdrMod) -> EffectivePdr;
```

Funktionsnavnet er dokumentationen af mekanikken. Hvis der ikke findes en navngivet konvertering, findes mekanikken ikke.

### Konsekvenser
- ✅ Den dokumenterede primære fejlklasse elimineres på compile-tid
- ✅ Koden bliver selvdokumenterende for spilmekanikken
- ❌ Boilerplate. Afbødes med en `impl_fixed_newtype!` macro
- ❌ Kræver disciplin: fristelsen til at tilføje en bekvem `From` skal modstås. Dokumenteret som eksplicit forbud i crate-doc

## ADR-003 — Datastrategi og -proveniens

**Status:** **Accepted (låst)** — hybrid A+C

### Kontekst
Projektets største enkeltrisiko. Spillet patches ugentligt. Datakilder er community-vedligeholdte (Dark and Darker Wiki / spellsandguns, DarkerDB), ikke API'er. Wiki-HTML blander auto-genererede tal med manuelle community-noter og "needs further testing"-markører midt i celler.

### Beslutning
**Håndgodkendt versioneret JSON i repo er den eneste sandhedskilde. Scraping er et forslagsværktøj uden skriverettigheder.**

Konkret:

1. **Sandhedskilden** er menneskeredigerbare JSON-filer committet i repo'et, versioneret pr. patch-build (ADR-004). Alt hvad `assay-core` nogensinde ser, har passeret et menneske.

2. **`assay-scrape`** kører mod wiki/DarkerDB og producerer en **forslagsdiff mod det committede datasæt** — aldrig en overskrivning. Output er en diff-fil, ikke et datasæt.

3. **Review-porten:** forslagsdiffen behandles som en pull request og accepteres eller afvises felt for felt. Accept skriver til datasættet med proveniens-metadata (kilde, tidspunkt, reviewer).

4. **Fallback-garanti:** formatet forbliver menneskeredigerbart JSON. Projektet skal være fuldt funktionelt med scraperen død. Scraperen er en bekvemmelighed, ikke en afhængighed.

5. **Tillidsgrænsen er ensrettet:** `assay-data` afhænger aldrig af `assay-scrape`. Håndhævet i workspace-manifestet og testet.

6. **Attribution:** Dark and Darker Wiki er CC BY-SA 4.0. Attribution og licensnote i repo-roden og i hvert datasæt-manifest. Scraper kører med rate limiting og respekterer `robots.txt`.

### Begrundelse
Ren håndholdt (A) skalerer ikke til hundredvis af items × rarities × modifier-ranges. Ren scraping uden review fejler stille: når wiki-HTML ændrer sig, opdager du det først når tallene er forkerte — hvilket er præcis den fejltype hele projektet er designet imod.

Hybriden har desuden en strukturel gevinst: **forslagsdiffen og patch-diffen er samme problem.** `assay-diff` bygges én gang og bruges to steder. Et scraper-brud manifesterer sig som en støjende, åbenlys diff frem for stille korruption.

### Konsekvenser
- ✅ Frisk *og* pålidelig. Datasættet er altid håndgodkendt
- ✅ Scraper-brud er synlige, ikke stille
- ✅ `assay-diff` genbruges; ét stykke maskineri, to anvendelser
- ✅ Projektet overlever at kilden forsvinder
- ❌ Mest arbejde op front af de tre veje
- ❌ Review-porten er en manuel flaskehals hver patch. Accepteret — den er hele pointen
- ❌ Kræver at diff-outputtet er læsbart nok til at reviewe hurtigt (ADR-008)

## ADR-004 — Datasæt-schema og patch-versionering

**Status:** Accepted

### Kontekst
Datasæt skal kunne eksistere side om side i flere versioner, så diff er mulig. Entiteter skal kunne identificeres på tværs af patches, også når de omdøbes eller ændrer værdier.

### Beslutning

**Versionsnøgle:** spillets build-id, med patch-label som menneskevenligt alias.

```
data/
├── 0.17.149.9316/          # hotfix-122
│   ├── manifest.json
│   ├── classes.json
│   ├── curves.json
│   ├── items.json
│   ├── perks.json
│   └── skills.json
└── 0.17.150.9384/          # hotfix-123
    └── …
```

**Stabile entitets-ID'er:** slug-baserede, tildelt én gang, aldrig genbrugt.
`item.flanged_mace`, `perk.rogue.lethal_mark`, `skill.fighter.fortified_ground`, `class.rogue`

ID'et er permanent selv hvis spillets visningsnavn ændrer sig. Omdøbning håndteres via eksplicit `renamed_from`-felt (ADR-008), aldrig heuristisk.

**Manifest med proveniens pr. fil:**
```json
{
  "build": "0.17.150.9384",
  "label": "hotfix-123",
  "released": "2026-08-13",
  "previous": "0.17.149.9316",
  "sources": [
    { "file": "items.json", "origin": "wiki:spellsandguns",
      "scraped": "2026-08-18T09:12:00Z", "reviewed": true }
  ]
}
```

**Kurver som data, ikke kode.** Attribut→derived-mappingerne (Strength → Physical Power Bonus, Armor Rating → PDR) er selv genstand for balanceændringer og skal derfor ligge i `curves.json` som punktsæt med defineret interpolation. Hardkodede kurver ville betyde en kodeændring hver gang Ironmace justerer skalering.

**Rarity-varianter:** et item har én base-definition plus per-rarity modifier-ranges. Season 10 ændrede uniques til at rulle **2 modifiers med op til 2× tidligere maksværdi** — schemaet skal modellere antal ruller og range separat, ikke som en flad værdi.

### Konsekvenser
- ✅ Flere versioner side om side; diff bliver trivielt
- ✅ Omdøbninger bryder ikke identitet
- ✅ Kurveændringer kræver ingen kodeændring
- ❌ Datavolumen duplikeres pr. version. Accepteret — JSON komprimerer godt, og historik er en feature
- ❌ Interpolation af kurver i fixed-point kræver dokumenteret rundingsregel (ADR-001)

## ADR-005 — Resolution pipeline

**Status:** Accepted — **kritisk, må ikke ændres uden ny ADR**

### Kontekst
Rækkefølgen af statberegning er ikke kosmetisk. En forkert ordre giver tal der ser rigtige ud og består overfladisk inspektion.

### Beslutning
Pipelinen er en sekvens af eksplicitte, typede, rene stadier. Låst rækkefølge:

```
1. Klassens base-attributter              Rogue: STR 9, VIG 6, AGI 25, DEX 20, WILL 10, KNO 10, RES 25
2. + attributter fra gear-ruller          Dark Leather Leggings: DEX 1–5
3. + attributter fra perks/skills/party   Jokester +2 alle · Fortified Ground +3 alle
   └─── FØRST HER er attributsummen endelig ───
4. Attributter → derived stats via kurver STR → Physical Power Bonus
                                          AGI → Action Speed, Move Speed
                                          VIG → Health
5. + flade adds                           Move Speed Add, Physical Buff Weapon Damage
6. + procentuelle bonusser                Dagger Mastery 15% · Sword Mastery 5% Action Speed
7. Defensiv kæde                          Armor Rating → PDR-kurve → cap
                                          (Defense Mastery hæver cap fra 60% til 75%)
8. Situationelle mods holdes SEPARAT      PDR Mod · healing mods · debuff duration
```

**Trin 3 før trin 4 er ikke til forhandling.** Fortified Ground (+3 All Attributes inden for 33m) og Jokester (+2 inden for 6m) giver tilsammen +5 All Attributes. Anvendes de efter kurveopslaget, bliver Physical Power Bonus systematisk forkert — og det er præcis den synergi Rogue/Fighter-duoen bygger på.

**Trin 8 holdes separat, fordi Lethal Mark ikke er en del af forsvarerens statblok.** Den er en modifier på *udvekslingen*. Blandes de sammen, kan spørgsmålet "hvad er denne spillers PDR" ikke længere besvares uafhængigt af hvem der angriber.

**Sporbarhed:** hvert stadie er inspicerbart. CLI'en understøtter `--explain`, som udskriver hvert stadies input, transformation og output. Uden det er "hvorfor er dette tal sådan" ubesvarligt, og værktøjet kan ikke debugges mod spillets character sheet.

### Konsekvenser
- ✅ Party-buff-synergier beregnes korrekt
- ✅ `--explain` gør værktøjet verificerbart mod spillet
- ❌ Pipeline-stadier må ikke omarrangeres af bekvemmelighed. Ordren er testet som invariant (ADR-010)

## ADR-006 — Damage-applikationsmodel

**Status:** Accepted

### Kontekst
Skadesberegning involverer angriberens og forsvarerens statblokke plus kontekst (bagfra, headshot, aktive debuffs). Den kan ikke være en metode på nogen af parterne.

### Beslutning
Skade modelleres som en `Exchange` — et værdiobjekt der tager angriber, forsvarer og kontekst, og som er fuldstændig ren.

```rust
pub struct Exchange<'a> {
    attacker: &'a ResolvedStats,
    defender: &'a ResolvedStats,
    context:  ExchangeContext,   // hit location, angle, aktive debuffs
}
```

**Låst rækkefølge:**

```
1. Base damage fra våben/skill
2. × scaling coefficient                 Sneak Attack: 0% · Rupture: 75% · Caltrops: 100%
3. + Physical Power Bonus                Back Attack +30% anvendes her
4. + flad Buff Weapon Damage             Slayer +5 · Sword Mastery +2
5. − forsvarerens Armor Rating, reduceret af angriberens Armor Penetration
6. → PDR fra kurven, cappet
7. × PDR Mod (multiplikativt)            Lethal Mark −30%
8. + True Damage (upåvirket af 5–7)      Dagger Mastery +1
9. × hit location-multiplikator          headshot / airborne +2%
```

**Trin 2 er den mest konsekvensrige detalje i hele modellen.** Sneak Attack har 0% scaling og er derfor immun over for Hide-exit-straffen på −30% Physical Power Bonus. Modelleres scaling ikke eksplicit pr. skill, forsvinder den indsigt — og den er hele grundlaget for Rogue'ens korrekte opener i Season 10.

**Trin 8 efter reduktion:** True Damage lægges til efter hele reduktionskæden, aldrig før.

**Ikke i v1:** Trin 5–9 implementeres fuldt, men eksponeres kun som `Exchange::damage()` for enkelte slag. TTK-iteration, action speed-baseret DPS og healing-throughput er v2 (ADR-011).

### Konsekvenser
- ✅ Skade er en ren funktion af tre inputs; trivielt testbar
- ✅ Scaling pr. skill gør 0%-mekanikken synlig i stedet for skjult
- ❌ `ExchangeContext` risikerer at vokse. Holdes i skak ved at kræve ADR for hvert nyt felt

## ADR-007 — Repræsentation af usikkerhed

**Status:** Accepted

### Kontekst
Kildedataene er ufuldstændige. Wiki'en markerer selv felter som uverificerede. Mindst seks åbne mekanikspørgsmål påvirker beregninger direkte: Ambush' buff-forbrug, Trickster på ikke-knive, Dual Strikes on-hit-dobbeltapplikering, Shield Masterys buffvindue, Victory Strikes reset-semantik, Shadowsteps gyldige mål.

Et analyseværktøj der ikke kan skelne "dette tal er rigtigt" fra "dette tal er et gæt" er værre end intet værktøj, fordi det får brugeren til at handle på gæt med selvtillid.

### Beslutning
Tillidsgrad er en førsteklasses del af domænemodellen.

```rust
pub enum Confidence<T> {
    Verified(T),                                   // patch notes eller egen test
    Unverified(T),                                 // wiki/community, ikke bekræftet
    Unknown { assumed: T, note: &'static str },    // antagelse med begrundelse
}
```

**Propageringsregel:** resultatets tillidsgrad er **minimum** af alle inputs. Én `Unverified` værdi i en kæde gør hele resultatet `Unverified`.

**Outputkrav:** CLI'en markerer resultater visuelt efter tillidsgrad og lister hvilke inputs der degraderede resultatet. `--strict` fejler i stedet for at rapportere, hvis noget er under `Verified`.

Datasættet bærer tillidsgrad pr. felt, sat under review (ADR-003).

### Konsekvenser
- ✅ Brugeren ved hvornår et tal kan handles på
- ✅ De åbne mekanikspørgsmål bliver synlige i outputtet i stedet for at forsvinde
- ✅ `--strict` giver en klar liste over hvad der bør testes i spillet
- ❌ `Confidence<T>` gennemsyrer signaturer. Afbødes med kombinator-helpers frem for manuel matching overalt

## ADR-008 — Patch-diff semantik

**Status:** Accepted

### Kontekst
"Patch-diff" dækker to forskellige spørgsmål, som ofte forveksles: hvad ændrede sig i *dataene*, og hvad ændrede sig for *mine builds*. Begge er nødvendige; kun det andet er handlingsanvisende.

### Beslutning
To diff-niveauer, klart adskilt.

**Niveau 1 — datasæt-diff.** Strukturel sammenligning mellem to versioner. Kategorier: `Added`, `Removed`, `Modified { field, from, to }`, `Renamed { from_id, to_id }`.

Omdøbning detekteres **ikke** heuristisk. Den udtrykkes eksplicit i datasættet via `renamed_from`, sat af mennesket under review. Heuristisk rename-detektion er en kilde til stille forkerte diffs, og hele projektet er designet imod netop det.

**Niveau 2 — impact-diff.** Givet et korpus af loadouts og to datasætversioner: resolvér hvert loadout i begge og rapportér *statdeltaer*. Dette er outputtet der besvarer det spørgsmål der reelt stilles hver torsdag.

```
$ assay diff hotfix-122 hotfix-123 --loadouts fixtures/duo/

rogue-lethal-artillery
  Physical Power Bonus        +0.00%   (uændret)
  Move Speed                 306 → 306 (uændret)
  ⚠ perk.rogue.lethal_mark   reapplicable: false → true

fighter-anvil
  Move Speed (Sprint aktiv)  339 → 333  (−6)   ← Sprint 15 → 13 MS add pr. stack
  Weapon Damage (flanged)     -1                ← HF123 item-nerf
  Armor Penetration          15% → 10%          ← HF123 item-nerf
```

**Output:** struktureret JSON (maskinlæsbart, stabilt sorteret) plus menneskelæsbar tabel. JSON er det primære; tabellen er en rendering.

**Genbrug:** samme motor driver scraper-forslagsdiffen fra ADR-003. Ét stykke maskineri, to anvendelser.

### Konsekvenser
- ✅ Besvarer "holder mit build stadig" på sekunder
- ✅ Ingen falske renames
- ✅ Genbrug mod scraper-porten
- ❌ Kræver at loadout-korpuset vedligeholdes for at impact-diff har værdi
- ❌ Eksplicit `renamed_from` betyder manuelt arbejde ved omdøbninger. Sjældent nok til at være acceptabelt

## ADR-009 — Loadout-format

**Status:** Accepted

### Kontekst
Loadouts skal kunne skrives i hånden, versioneres i git, diffes læsbart, og — afgørende — **resolveres mod flere datasætversioner**.

### Beslutning
**TOML**, menneskeskrivbart, og **versions-agnostisk**.

Et loadout refererer udelukkende entitets-ID'er. Det pinner ikke en datasætversion. Versionen leveres ved resolve-tid.

```toml
name  = "rogue-lethal-artillery"
class = "class.rogue"
level = 15

perks  = ["perk.rogue.dagger_mastery", "perk.rogue.poisoned_weapon",
          "perk.rogue.lethal_mark",    "perk.rogue.jokester"]
skills = ["skill.rogue.sneak_attack",  "skill.rogue.weakpoint_attack"]

[weapons]
main_hand = { id = "item.rondel_dagger",   rarity = "epic", roll = "max" }
off_hand  = { id = "item.castillon_dagger", rarity = "rare", roll = "max" }
utility   = ["item.throwing_knife"]

[armor.legs]
id = "item.dark_leather_leggings"
rarity = "epic"
rolls = { dexterity = 4, move_speed = 2 }   # eksplicitte værdier vinder over `roll`

[party]                                      # eksterne buffs, se ADR-005 trin 3
fortified_ground = true                      # +3 All Attributes
```

**Roll-håndtering:** `roll = "min" | "max" | "mid"` som bekvemmelighed, men eksplicitte `rolls`-værdier har forrang. Analyser skal kunne køres både på realistisk gear og på teoretisk BiS.

**Versions-agnosticismen er hele forudsætningen for ADR-008 niveau 2.** Pinnede loadouts kunne ikke resolveres i to versioner og impact-diff ville være umulig.

### Konsekvenser
- ✅ Samme loadout resolverer i enhver datasætversion → impact-diff virker
- ✅ TOML differ læsbart i git
- ❌ Et loadout kan blive ugyldigt hvis et item fjernes i en senere patch. Håndteres som en eksplicit `LoadoutError::EntityNotInDataset` med versionsangivelse — hvilket i sig selv er nyttigt information

## ADR-010 — Teststrategi

**Status:** Superseded af rev 2

### Kontekst
Værktøjets eneste værdi er korrekthed. Et forkert tal der ser rigtigt ud er værre end en crash.

### Beslutning
Fem testlag:

**1. Renhedstest.** CI fejler hvis `assay-core` refererer `std::fs`, `std::net`, `std::process`, `reqwest`, `tokio` eller `assay-data`. Fejler hvis `assay-data` refererer `assay-scrape`.

**2. Golden fixtures.** Håndberegnede loadouts med forventede statblokke, verificeret mod spillets character sheet. Minimum: begge duo-builds fra Rogue/Fighter-analysen, plus én naked-baseline pr. klasse (base-statblokken fra wiki'en er en gratis, autoritativ fixture).

**3. Property tests** (proptest):
- Monotonicitet: øget Armor Rating sænker aldrig PDR
- Cap-invariant: PDR overstiger aldrig det gældende cap (60%, eller 75% med Defense Mastery)
- Pipeline-ordre: attributter fra party-buffs påvirker derived stats — dvs. et loadout med Fortified Ground har strengt højere Physical Power Bonus end uden, når STR-kurven er ikke-flad
- Determinisme: samme input → byte-identisk output, gentaget

**4. Schema-validering.** Hver datasætversion valideres mod schemaet ved test. Ingen ukendte felter, ingen manglende obligatoriske felter, alle `renamed_from` peger på eksisterende ID'er i forgængerversionen.

**5. Kryds-versionstest.** Hvert fixture-loadout skal resolvere i hver tilgængelig datasætversion, eller fejle med en eksplicit, forventet fejl. Dette fanger schema-drift tidligt.

**Dækningskrav:** `assay-core` skal have branch coverage på alle pipeline-stadier og alle damage-trin. Ingen numerisk kode uden mindst én golden fixture.

### Konsekvenser
- ✅ Korrekthed er testet, ikke antaget
- ✅ Wiki'ens base-statblokke giver gratis autoritative fixtures
- ✅ Kryds-versionstest fanger schema-drift før den rammer brugeren
- ❌ Golden fixtures skal genverificeres når en patch faktisk ændrer de underliggende tal — men det er præcis hvad impact-diff er til for at opdage

## Definition of done — v1

Du kan bygge Rogue- og Fighter-loadoutsene fra duo-analysen i værktøjet, få statblokke ud der matcher spillets character sheet inden for afrundingsfejl, og køre:

```
$ assay diff hotfix-122 hotfix-123 --loadouts fixtures/duo/
```

og se præcis hvad Sprint-trimmen og item-nerfene gjorde ved dem — med tillidsmarkering på hvert tal.
